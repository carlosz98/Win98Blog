🐛 Troubleshooting: "My file isn't showing up"

Ran into this while trying to load an OrderForm project (an HTML form that submits to a PHP file).

Symptom: visiting localhost/OrderForm/ showed nothing / a 404, or the browser kept showing an old page.

Cause: the two related files ended up saved in different folders — orderform.html had been saved into htdocs/MAC272/, while processorder.php was saved into htdocs/OrderForm/. Since the form submits to processorder.php as a relative path, it needs to sit right next to the HTML file, in the same folder. There was also no index.php/index.html inside OrderForm/, so visiting just the folder URL had nothing to auto-load.

Fix:

  1. Pick one project folder (in htdocs) — here, OrderForm.

  2. Move both files into that same folder, so they sit side by side.

  3. Visit the exact path + filename in the browser: localhost/OrderForm/orderform.html.

How to double-check next time:

  • In VS Code's Explorer sidebar, confirm both files show up nested under the same folder — not spread across two.

  • The URL in the browser must match: localhost/<folder>/<filename> exactly (case-sensitive), matching where the files actually live on disk.

  • If a page still won't update, hard refresh (Cmd+Shift+R) to rule out a stale browser cache.

Forms & $_POST

Why POST? An HTML form's method attribute controls how its data is sent to the server:

  • GET — appends form data to the URL as a query string (e.g. ?tiresqty=2&oilqty=1). Visible in the address bar, limited in length, and gets cached/bookmarked — fine for things like search boxes, not for real data submission.

  • POST — sends form data in the body of the HTTP request instead of the URL. Not visible in the address bar, no practical size limit, and doesn't get cached or bookmarked — the right choice whenever a form is submitting/creating/changing data (like an order form), or when the data shouldn't be exposed in a URL.

On the PHP side, data sent via POST is read using the $_POST superglobal array, keyed by each input's name attribute — e.g. $_POST['tiresqty'] grabs the value from <input name="tiresqty">.

orderform.html (the form):

  • <form action="processorder.php" method="post"> — when submitted, the browser sends this form's data to processorder.php using POST (see the Forms & $_POST note above for why).

  • <input type="submit" value="Submit Order" /> — the button that triggers the form to actually send its data.

processorder.php (the results page):

  • Standard HTML skeleton (<!DOCTYPE html>, <head>, <title>, <body>) — this is the page the browser lands on after submitting the form.

  • <h1> / <h2> — the page heading and subheading, plain HTML, no PHP involved.

  • Inside the <?php ... ?> block, three echo statements build one HTML paragraph across three lines:

    • echo "<p>Order Processed "; — opens a <p> tag and starts the message.

    • echo date('H:i, jS F Y'); — inserts the current server date/time. Breaking down the format string: H:i = 24-hour time (e.g. 18:27), jS = day of month with ordinal suffix (e.g. 24th), F = full month name (e.g. September), Y = 4-digit year (e.g. 2026).

    • echo "</p>"; — closes the paragraph.

  • $_POST['tiresqty'] (etc.) — pulls each submitted value out of the $_POST superglobal, matching the name attribute from the form, and stores it in a short variable ($tireqty, $oilqty, $sparkqty) for easy reuse.

  • htmlspecialchars() — wraps user-submitted values before printing them, converting characters like < > & " into safe HTML entities. This prevents a user from breaking the page's HTML or injecting malicious script tags (a basic XSS protection) — always good practice when echoing anything a user typed.

New addition — pricing with define():

define('tireprice', 100);
define('oilprice', 21);
define('sparkprice', 6);

$totalamount = $tireqty * tireprice
+ $oilqty * oilprice
+ $sparkqty * sparkprice;

  • define('name', value) creates a constant — like a variable, but its value can never change once set. Unlike variables, constants are written without a $ when used (tireprice, not $tireprice).

  • Constants are handy here because prices are fixed values that shouldn't accidentally get reassigned somewhere else in the script.

  • The math relies on normal order of operations — multiplication (*) happens before addition (+), so each item's quantity × its price is calculated first, then the three results are summed. No parentheses needed, though adding them (($tireqty * tireprice) + ...) can make the intent clearer to read.

number_format():

number_format($totalamount, 2) formats a number as a string with commas for thousands and a fixed number of decimal places (2 = cents) — e.g. 1234.5 becomes 1,234.50. Useful for displaying prices cleanly.

That 2 is the function's second parameter — it tells number_format() how many decimal places to show, which is why it's standard for money (guarantees cents always show, e.g. 682 becomes 682.00 instead of just 682).

Built-in Functions Used So Far

PHP ships with thousands of built-in functions — ready to use with no setup. Here's what each one we've used actually does:

  • echo — not technically a function (it's a language construct), but works like one: outputs one or more strings to the page. Can take multiple comma-separated arguments (echo "a", "b";) or be chained with ..

  • date() — returns the current server date/time, formatted according to a format string you pass in (e.g. 'H:i, jS F Y'). Each letter in the format string means something specific (H = hour, i = minutes, j = day, S = ordinal suffix, F = full month, Y = year).

  • htmlspecialchars() — takes a string and converts HTML-sensitive characters (<, >, &, ") into safe HTML entities before printing. Protects against a user's input accidentally (or maliciously) breaking the page's HTML or injecting script tags.

  • number_format() — takes a number and returns it as a nicely formatted string, with thousands separators and a fixed number of decimal places (e.g. number_format(1234.5, 2) → "1,234.50").

  • define() — not a formatting function, but a built-in used to create a constant: a named value that can't be changed later in the script.

Why the . (Dot) Operator?

In PHP, . is the string concatenation operator — it joins (glues together) two pieces into one string. This is different from many other languages (JavaScript, Java, etc.) where + is used to join strings — in PHP, + is reserved strictly for math, so a separate symbol (.) exists just for combining text.

$name = "Carlos";
echo "Hello " . $name . "!";  // → Hello Carlos!

This matters because mixing them up causes real bugs:

  • "5" + "3" → 8 (PHP treats both as numbers and adds them)

  • "5" . "3" → "53" (PHP treats both as text and glues them together)

That's exactly why, earlier, $tireqty * tireprice + $oilqty * oilprice + ... uses + (real math on numbers) while building the output string ("Subtotal: " . number_format(...)) uses . (joining text) — same script, two different jobs for two different operators.

Totaling the order:

  • $totalqty = 0; initializes the variable first (good habit before adding to it).

  • $tireqty + $oilqty + $sparkqty — PHP automatically converts these form values (technically strings) into numbers to do the math. This is called type juggling — no manual conversion needed for simple numeric strings.

  • The result is concatenated with . into the output string, same pattern as before.

Comparison Operators: == vs. =

These look similar but do completely different jobs — mixing them up is one of the most common beginner bugs.

  • = — the assignment operator. It sets a variable's value.

    $a = $b;  // $a now HOLDS whatever $b's value is

  • == — the equality (comparison) operator. It checks whether two values are equal, and returns true or false — it does not change either variable.

    $a == $b;  // checks: does $a's value equal $b's value? (true or false)

Why it matters: using = where you meant == doesn't cause an error — it silently assigns instead of comparing, which can quietly break your logic:

if ($a = $b) {   // ⚠️ assigns $b's value to $a, then checks if that value is "truthy"
    // this can run even when you meant to check equality
}

if ($a == $b) {  // ✅ correctly compares $a and $b without changing either
    echo "They're equal!";
}

Other comparison operators (from the if/else notes earlier), same family as ==:

!=not equal
!==not equal in value or type

>= / <=greater than or equal / less than or equal

Rule of thumb: one = sets a value; two or three (==, ===) check one.

Checking a Variable's Type — gettype()

//type of the variable

echo gettype($tireqty) . '<br>';

gettype($tireqty) — a built-in function that returns a string naming the variable's current data type: "string", "integer", "double" (float), "boolean", "array", "NULL", etc. Handy for debugging — e.g. confirming that $tireqty (pulled from $_POST) actually arrives as a "string", even though it's later used in math thanks to type juggling.

⚠️ Heads up: the line as typed has a small typo — gettype($tireqty): '<br>' uses a colon (:) instead of the concatenation operator (.). A colon there isn't valid PHP syntax in this context and will throw a parse error. Corrected:

echo gettype($tireqty) . '<br>';

settype() — the counterpart to gettype(): instead of just checking a variable's type, it actually changes it, converting the variable in place.

settype($tireqty, 'integer');
echo gettype($tireqty); // now prints "integer" instead of "string"

  • Takes the variable itself (not a copy) plus the target type as a string ('integer', 'string', 'float'/'double', 'boolean', 'array').

  • Unlike gettype() (which returns a new string and leaves the variable untouched), settype() modifies $tireqty directly — it returns true/false for success, not the value.

  • Useful when you want to be explicit and guarantee a value really is a number (instead of relying on PHP's automatic type juggling), e.g. right after pulling something out of $_POST.

The is_*() family — type-checking functions:

Instead of comparing gettype()'s string output, PHP has a dedicated is_*() function for each type. Each one takes a variable and returns true or false directly — cleaner than writing gettype($x) == 'integer'.

FunctionChecks for
is_array()Is it an array?
is_string()Is it a string?
is_int() / is_integer() / is_long()Is it a whole number (int)? — all three are aliases for the same check
is_float() / is_double()Is it a decimal number? — is_double() is just an alias for is_float()
is_bool()Is it true/false?
is_null()Is it null (no value)?
is_numeric()Is it a number or a numeric string (e.g. "42")? — useful for validating form input
if (is_numeric($tireqty)) {
    echo "Valid quantity<br>";
} else {
    echo "That's not a number!<br>";
}

Why these are useful: validating form input is the big one — since everything from $_POST arrives as a string, is_numeric() is a quick way to check "did the user actually type a number?" before doing math with it, rather than trusting the input blindly.
