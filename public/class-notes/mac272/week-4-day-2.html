Topic 1: Login Form (HTML form + PHP processing)

A login form is the simplest example of HTML and PHP working together. HTML builds the form the user sees. When the user clicks submit, the browser sends the form data to the server, Apache hands the request to PHP, and PHP reads the data, checks it, and sends back a response.

Flow: Browser (HTML form) → Apache → PHP script → response back to the browser

Syntax

<form action="file.php" method="POST">
  <input type="text" name="fieldname">
  <input type="submit" value="Send">
</form>

  • action is the PHP file that receives the data.

  • method is how the data is sent. POST sends it in the request body (not shown in the URL). GET puts it in the URL.

  • name on each input is the key PHP uses to read the value.

  • required makes the browser block submitting an empty field.

  • label for="x" links the label to the input with id="x".

PHP basics used today:

  • <?php ... ?> opens and closes a block of PHP code.

  • $_SERVER["REQUEST_METHOD"] tells you how the page was requested (GET or POST).

  • $_POST['name'] reads a value sent by a POST form, using the input's name attribute.

  • == compares two values. && means AND.

  • echo prints output to the page. // starts a one-line comment. if / else runs code depending on a condition.

Login.php (first version, form and PHP in one file)

<!DOCTYPE html>
<html>

<title>Login Form</title>
</head>
<body>

<label for="username">User Name:</label>
<input type="text" id="username" name="username" required>

Line-by-line

  • Lines 1–18: the HTML page with the login form. type="password" hides the characters as the user types.

  • Line 8: the form sends its data with POST to login_process.php.

  • Line 21: checks that the page was reached by a form submission (POST) before processing anything.

  • Lines 22–23: store the submitted username and password in variables. PHP variables start with $.

  • Line 25: compares the input to the hardcoded values John and 123. Both must match.

  • Lines 26 and 28: echo prints a green message if correct, a red message if not.

Things to watch for

  • File mismatch: the form's action points to login_process.php, but the validation code sits inside Login.php. If the form posts to login_process.php, the validation needs to live in that file (or change action to Login.php to process on the same page). The two-file version below fixes this.

  • Run it through Apache: PHP only runs when Apache serves the file, at http://localhost/login/Login.php. Opening the file directly from the folder shows the PHP code as text.

  • Case sensitive: 'John' and 'john' are different values.

  • Hardcoded credentials are only for practice. Real logins check a database (MySQL) and store hashed passwords.

  • Stricter comparison: === also checks the data type and is generally safer than ==.

  • Escape output: when printing user input back on a page, wrap it with htmlspecialchars() to prevent XSS.

  • Only the name attributes matter for PHP. If name="username" changes in the form, $_POST['username'] must change to match.

Topic 2: Form Handling (class handout: PHP Tutorial Part 7)

These notes follow the class handout, with plain-language explanations added.

The big picture

  • Static webpage: plain HTML. The content does not change unless something else (JavaScript or server-side code) changes it.

  • Web application: a set of pages hosted on a web server (like Apache) that uses server-side code (PHP, Node.js, Python) for logic, data processing, and databases.

  • How they talk: the browser is the HTTP client. It sends a request (open a page, submit a form), the server runs the code, and the server sends back a response (HTML). HTTPS is the same thing with encryption.

  • Form handling in PHP: collecting, validating, and processing the data a user submits through an HTML form.

In simple words: the user fills in a form, the browser packs the data into a request, Apache gives it to PHP, and PHP reads it and decides what to show back.

Basic HTML form

<!DOCTYPE html>
<html lang="en">
<head>
    <title>PHP Form Handling</title>
</head>
<body>
    <form action="process.php" method="post">
        <label for="name">Name:</label>
        <input type="text" id="name" name="name">
        <br><br>
        <label for="email">Email:</label>
        <input type="email" id="email" name="email">
        <br><br>
        <input type="submit" value="Submit">
    </form>
</body>
</html>

  • action: the PHP file that receives and processes the data (here process.php).

  • method: how the data is sent, GET or POST.

  • name on each input: this becomes the key PHP uses to read the value. The most important point in the handout: any form element in an HTML page is automatically available to your PHP script.

  • type="email": the browser checks that the text looks like an email address before submitting.

Basic workflow

  1. HTML form: create the form to collect user input.

  2. Form submission: the browser sends the data with POST or GET to a PHP script.

  3. PHP script: reads the data with $_POST, $_GET, or $_REQUEST.

  4. Processing: validate the data, process it, and optionally store it in a database.

  5. Response: PHP prints a message or redirects the user to another page.

Superglobals

Superglobals are predefined PHP variables that are always available, in any function, class, or file, with no global keyword needed. Most are associative arrays: key-value pairs where the key is a name and the value is the data.

$person = ['name' => 'John', 'age' => 25];
echo $person['name'];   // John

The handout covers the first five in detail. The last four come later in the course.

$GLOBALS is an array of all global variables. It lets a function read or change a global variable from inside the function. The other way is the global keyword (see Week 4, Day 1, variable scope and Lab #2 Q4).

<?php
$x = 10;
$y = 20;
function sum() {
    $GLOBALS['z'] = $GLOBALS['x'] + $GLOBALS['y'];
}
sum();
echo $z;   // Outputs: 30
?>

Why it is needed: variables created outside a function are not visible inside it by default (this is called scope). $GLOBALS reaches through that wall.

$_SERVER holds information about the server and the current request.

$_SERVER['PHP_SELF'];          // filename of the currently running script
$_SERVER['SERVER_NAME'];       // the server's name
$_SERVER['REQUEST_METHOD'];    // how the page was requested (GET or POST)

$_POST holds the variables received with the HTTP POST method. A form uses POST when method="POST". When the user clicks submit, the data goes to the file named in action.

Form and processor in two files:

<form method="POST" action="demo_request.php">
    Name: <input type="text" name="fname">
    <input type="submit">
</form>
// demo_request.php
$name = $_POST['fname'];
echo $name;

Form and PHP in the same file:

<html>
<body>
<form method="POST" action="<?php echo $_SERVER['PHP_SELF'];?>">
  Name: <input type="text" name="fname">
  <input type="submit">
</form>
<?php
if ($_SERVER["REQUEST_METHOD"] == "POST") {
  $name = ($_POST['fname']);
  if (empty($name)) {
    echo "Name is empty";
  } else {
    echo $name;
  }
}
?>
</body>
</html>

  • PHP_SELF: the current file's name, so the form sends its data back to the same page.

  • action="": leaving the action empty also submits to the current page, and is the safer choice (printing PHP_SELF straight into the page can be abused by attackers).

  • empty($name): true when the value is blank (empty string, 0, or not set).

  • Why the REQUEST_METHOD check: the first time the page loads (GET) the form is only displayed. The PHP block runs only after the form is submitted (POST).

Walkthrough: the same-file form, step by step

The confusing part is that one file does two jobs and runs twice: once to show the form, and once more after the user submits it. Each time, PHP reads the file from top to bottom.

Run 1: you open the page (a GET request)

  1. PHP reaches action="<?php echo $_SERVER['PHP_SELF'];?>" and fills in the current file's name. If the file is /login/form.php, the browser receives action="/login/form.php".

  2. The form is sent to the browser and displayed.

  3. PHP reaches the if. $_SERVER["REQUEST_METHOD"] is GET (you only opened the page), so the condition is false and PHP skips everything inside it.

  4. Result: you see an empty form and nothing else.

Run 2: you type a name and click submit (a POST request)

  1. The browser sends the data to the address in action, which is the same file.

  2. PHP runs the file again from the top and shows the form again.

  3. This time REQUEST_METHOD is POST, so the condition is true and PHP enters the block.

  4. $name = ($_POST['fname']); takes the value labeled fname from the form and stores it in $name. The extra parentheses change nothing.

  5. empty($name) checks if the box was left blank. If it was, the page prints Name is empty. Otherwise it prints what was typed.

What the browser actually receives after typing "Ana":

<form method="POST" action="/login/form.php">
  Name: <input type="text" name="fname">
  <input type="submit">
</form>
Ana

Why put the form and the PHP in one file? It is convenient for small examples, because the form and its result stay together. The login project uses two files instead (Login.php and login_process.php) to keep the form separate from the processing. Both ways work, and the idea is the same.

$_GET

Holds variables received in the URL. They arrive in two ways: a query string or an HTML form with method="GET".

A query string is data added to the end of a URL after the ?. Pairs are written key=value and joined with &.

<a href="demo_phpfile.php?subject=PHP&web=W3schools.com">Test GET</a>

This link sends two pairs: subject=PHP and web=W3schools.com.

<?php
echo "Study " . $_GET['subject'] . " at " . $_GET['web'];
?>

The . joins strings together (concatenation). Output: Study PHP at W3schools.com.

GET form:

<form action="welcome_get.php" method="GET">
    Name: <input type="text" name="name">
    E-mail: <input type="text" name="email">
    <input type="submit">
</form>

After submitting, the browser address becomes: welcome_get.php?name=John&email=john@example.com

<html>
<body>
Welcome <?php echo $_GET["name"]; ?><br>
Your email address is: <?php echo $_GET["email"]; ?>
</body>
</html>

Class demo output (GET form): the professor typed the name Adam and the email adam@gmail.com. The page showed:

Welcome Adam
Your email address is: adam@gmail.com

The address bar showed the data in the URL:

welcome_get.php?name=Adam&email=adam%40gmail.com

  • The data is in the URL because the method is GET, not POST. With POST the address bar would show only welcome_get.php, and the PHP would read $_POST["name"] instead of $_GET["name"].

  • %40 is how a URL writes the @ symbol. Browsers encode special characters in the URL, and PHP decodes them back, so $_GET["email"] still gives adam@gmail.com.

  • Each pair is name=value, and pairs are joined with &. The names come from the name attributes of the form inputs.

$_REQUEST

Contains data from $_GET, $_POST, and $_COOKIE together, so it works whichever method was used.

<?php echo $_REQUEST['fname']; // the value typed in the "fname" field ?>

Typo in the handout: the form field is named fname but the handout reads $_REQUEST['name']. The key must match the input's name attribute exactly, so it should be $_REQUEST['fname']. Using $_POST or $_GET is usually clearer because you know where the data came from.

GET vs POST

Both methods build an array of key-value pairs: the keys are the form control names and the values are what the user typed. $_GET and $_POST are superglobals, so they work anywhere in your code.

GETPOST
Where the data goesIn the URL (query string)Inside the body of the HTTP request
Visible to othersYes, names and values show in the address barNo
Size limitSmall (the handout says about 2000 characters)Much larger (default 8 MB, set by post_max_size in php.ini)

Rule from the handout: never use GET for passwords or other sensitive information. Developers prefer POST for sending form data.

When to use GET and when to use POST (login form example). The login form uses POST because GET would show everything the user typed. The address bar after clicking Log in:

MethodAddress bar after submitting
GEThttp://localhost/login/login_process.php?username=John&password=123&submit=Log+in
POSThttp://localhost/login/login_process.php

With GET the username and the password sit in plain sight in the URL. The submit=Log+in part appears too, because the button has a name.

Why that is a problem for a login:

  • Anyone looking at the screen sees the password in the address bar.

  • The browser saves the full URL in its history, so the password stays on the computer.

  • The URL can be copied, bookmarked, or shared, and the password goes with it.

  • Servers often log the URL of each request, so the password can end up in log files.

POST puts the data in the body of the request, so none of this appears in the URL. POST by itself is not encryption. Real sites also use HTTPS so the data is protected while it travels.

How to choose:

Short version to remember: GET asks for something to look at, POST sends something to be processed.

GET and POST in APIs and web applications. When working with APIs and web applications, two of the most common HTTP methods are GET and POST. An API is a way for programs to talk to each other over HTTP, and every request has a method (what you want to do) and a URL (where). The same two methods you use in HTML forms are used between apps.

GET vs POST in plain words. GET is a postcard and POST is a sealed envelope. A postcard (GET) has the message written on the outside: anyone who handles it can read it, and a copy can be kept. It is fine for "Please send me the menu." A sealed envelope (POST) has the message inside and only the address on the outside. It is the right choice for private or larger messages.

Short answers for a quiz:

  • GET: sends data in the URL, is visible, has a size limit, can be bookmarked, and should not be used for sensitive data.

  • POST: sends data in the body of the request, is not visible in the URL, has a much bigger limit, and is preferred for forms and sensitive data.

  • Both create an array of key-value pairs, and both superglobals ($_GET, $_POST) work anywhere in the code.

Browser redirection

The header() function with a Location: header sends the user to another page. Call exit right after it so the rest of the script stops running.

<?php
header("Location: http://www.google.com/");
exit;   // Always exit after a redirect to stop script execution.
?>
<?php
header('Location: welcome.php');   // a page inside our own site
exit;
?>

  • Call header() before any output. If anything has already been printed (an echo, HTML, even a blank line before <?php), PHP shows a "headers already sent" warning and the redirect fails.

  • Why exit: header() only asks the browser to go elsewhere. PHP keeps running the rest of the script unless you stop it.

  • Why header() must come first: an HTTP response has two parts, the headers (instructions for the browser, like "go to another page") and then the body (the visible page). Headers always go first. Once PHP prints anything, the body has started and it is too late to send headers.

Optional practice (redirect after a correct login):

// login_process.php
if ($username == 'John' && $password == '123') {
    header('Location: welcome.php');
    exit;
} else {
    echo "<p style='color: red;'>Username or password is not correct.</p>";
}
<?php
// welcome.php
echo "<h1>Welcome!</h1>";
?>

The redirect has to run before any output, so in login_process.php keep the PHP block at the very top of the file.

Understanding the "why" behind the code

Syntax is mostly a set of rules that PHP and the browser need in order to understand you, and each piece has a reason.

The restaurant analogy. A form is like ordering at a restaurant.

  • The HTML form is the order slip. The user fills it in.

  • name="username" is the label of each item on the slip. The kitchen finds your order by these labels.

  • Apache is the waiter. It takes the slip to the kitchen.

  • PHP is the kitchen. It reads the slip, decides what to do, and prepares the answer.

  • echo is the plate that comes back. The browser only ever sees the finished plate (HTML), never the recipe (PHP code).

  • action is which kitchen gets the slip. method is how the slip is delivered (GET on a note shouted across the room, POST in a sealed envelope).

How to read a PHP line. Read it left to right as a sentence:

$username = $_POST['username'];

  1. $username is a box I am creating. I picked the name.

  2. = means put something in the box. It is not a question.

  3. $_POST is the built-in list of everything the form sent.

  4. ['username'] means find the item labeled username in that list.

  5. ; means this instruction is finished.

In English: "Take the value labeled username from the form data and store it in a box called $username."

Why the quotes look mixed up

echo "<p style='color: green;'>Your information is correct.</p>";

The PHP text starts and ends with double quotes ("). The HTML inside needs its own quotes for style=, so it uses single quotes ('). Mixing the two keeps the quotes from colliding. If you used double quotes both times, PHP would think the text ended early. You can swap them: '<p style="color: green;">...</p>' works too. Double-quoted text can hold variables: "Hello $name" prints the value, while single-quoted text prints $name literally.

Apache and PHP quick facts

  • Apache serves files from its document root. A file must be inside that folder (or a subfolder) to be reached at http://localhost/..., and the URL path follows the folders (localhost/login/Login.php).

  • PHP runs only when Apache processes the file, and the file needs the .php extension. A .html file containing PHP code is shown as plain text.

  • Use http://localhost, not file://. Double-clicking a file opens it without Apache, so PHP never runs.

How the regular expression reads: /^[a-zA-Z ]*$/

In plain English: "From the very start to the very end, there are only letters and spaces." Picture it as a door check: the pattern looks at every character, one by one. Letter? Fine. Space? Fine. Anything else (a number, !, @)? Rejected.

preg_match(pattern, text) asks "does this text fit this pattern?" It returns 1 if yes and 0 if no. You do not need to memorize regular expressions. You need to be able to read them.

The trim() function (requirement 3)

trim(string)

  • What it does: removes spaces from the start and the end of a text. It also removes tabs and line breaks at the ends.

  • What it does not do: it does not touch spaces between words, so Ana Lopez stays Ana Lopez. That matters because the name rule allows white space.

  • It returns a new text. The original variable is not changed unless you save the result.

Common mistake: writing trim($name); on its own line does nothing, because the cleaned text is thrown away. Save it: $name = trim($name);. Related functions: trim() (both ends), ltrim() (start only), rtrim() (end only). trim() is not the same as removing every space: str_replace(" ", "", $name) would turn Ana Lopez into AnaLopez, which is not what the lab wants.

The filter_var() function (requirement 4)

filter_var(value, filter)
if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {

How the code works

  1. Variables first. Every field gets a value variable and an error variable, all empty. The page needs them even on the first load, because the form prints them. Chained $a = $b = ""; sets several variables to the same value.

  2. Validation runs only after submit. The REQUEST_METHOD == "POST" check means that on the first load the form shows with no errors.

  3. trim($_POST["name"] ?? ""). $_POST["name"] reads the typed value. ?? "" means "if that key is missing, use an empty string" and prevents a warning for fields that were not sent. trim(...) removes spaces at the start and end (requirement 3).

  4. if / elseif for each field. The first check is "is it empty?" (required). Only if it is not empty does PHP run the second check (letters only, valid email, digits only). Each failed check writes an error message into that field's error variable. Only one message per field is shown, and the most basic problem (empty) comes first.

  5. Gender is different. Text boxes are always sent, even when empty. A radio group with nothing selected is not sent at all, so empty($_POST["gender"]) is true when the user picked nothing.

  6. Success means no errors. The big if checks that every error variable is still empty (&& needs all of them).

  7. Keeping what the user typed. value="<?php echo htmlspecialchars($name); ?>" puts the typed text back into the box after an error, so the user does not retype everything. For radio buttons, checked is printed on the matching option.

  8. htmlspecialchars(). Turns characters like < and > into harmless text before printing user input back into the page. This stops a user from inserting HTML or JavaScript into your page (an XSS attack).

  9. The <?php if ($success) { ?> ... <?php } else { ?> ... <?php } ?> structure. PHP can open and close around HTML. If the registration succeeded the page shows the success message, otherwise it shows the form.

Why there is no required attribute in the HTML: the lab asks for PHP validation, and a browser required would stop the form before PHP ever checks it. Adding it is an optional extra, and the PHP checks are still needed.

Part-by-part reasoning

  • Part 1, variables at the top. The form prints these variables on the very first page load, before anything was submitted. A variable that does not exist causes an "undefined variable" warning. Each field needs two variables: $name (what the user typed, cleaned with trim()) and $nameErr (the error message, empty if there is no problem). They cannot share one variable, because after a failed check you need both the typed text and the message. $name is not the form field: name="name" and $_POST["name"] are the data from the browser, and $name is your own variable that stores a cleaned copy.

  • What if $success = false; is left out? The page still works, but PHP shows an Undefined variable $success warning, because $success is only set to true when everything passed. Starting every variable with a known value is a good habit.

  • Part 2, the POST check. Without it, the user would see "required" errors before typing anything.

  • Part 3, name. trim() first, because a name made only of spaces would otherwise count as "filled in". The required check comes before the pattern, because the pattern's * accepts an empty text. elseif shows only one message per field.

  • Part 4, email. filter_var is more reliable than writing your own pattern. Trim first so a leading space does not make a good address invalid.

  • Part 5, gender. No trim() or == "", because an unselected radio group is not sent at all and empty() handles a missing key without a warning. The else saves the value so the page can re-select the chosen option after an error elsewhere.

  • Part 6, street, city, state. The lab asks for only a required check on these three. trim() still matters, so a box filled only with spaces does not count as an answer.

  • Part 7, zip. ctype_digit and not is_numeric: is_numeric also accepts things like 1.5, -3, and 1e5, while ctype_digit accepts only the characters 0 to 9. The zip stays text, because a zip like 02134 would lose its leading zero if it were converted to a number.

  • Part 8, the success check. One failed field means the whole form is not valid, so && needs all of the error variables to be empty. The $success flag lets the HTML below decide what to show without repeating the checks.

  • Parts 9 to 12, the HTML. Only one of the two branches (success or form) is sent to the browser. method="POST" keeps form data out of the URL, and the action is the same file. The red <span> with * marks the field as required and shows its error message in the same place, like the lab sample. All three radio buttons share name="gender", which makes them a group where only one can be selected, and checked re-selects the chosen option. The final <?php } ?> closes the else opened in Part 9, and a missing } makes PHP show a parse error.

The big picture: parts 1 to 8 collect the data, clean it with trim(), check each rule, and record errors. Parts 9 to 12 show a success message when there are no errors, or the form again with the messages and the user's text. The rule that links both halves: every name in the HTML must match the key used in $_POST.

Comparison: the W3Schools form validation example vs the lab code

The lab code follows the same pattern as the W3Schools "PHP Form Validation" example (Name, E-mail, Website, Comment, Gender). Both start with the variables, check REQUEST_METHOD == "POST", write an error per field, and post the form back to itself with htmlspecialchars($_SERVER["PHP_SELF"]). The lab version goes further in several places.

Why htmlspecialchars() belongs on the output. Escaping when the value is read (as test_input() does) changes the stored text: Tom & Jerry becomes Tom &amp; Jerry, and escaping it again later would double-escape it. Keeping the raw text and escaping only when printing into HTML is the safer habit, and it is what the lab code does.

stripslashes() is no longer needed. It removed backslashes that old PHP versions ("magic quotes") added automatically. Modern PHP does not add them, so it is just a leftover in the W3Schools example.

Mistakes and traps to remember

  • A form name that does not match the key in $_POST / $_GET gives "Undefined array key" or nothing at all.

  • Opening the page with file:// instead of http://localhost, so PHP never runs.

  • Forgetting to save the file (a dot on the VS Code tab) so Apache serves the old version.

  • = vs == inside an if: if ($a = 5) is always true.

  • header() after any output gives "headers already sent", and forgetting exit lets the script keep running.

  • trim($name); on its own line does nothing: save the result with $name = trim($name);.
