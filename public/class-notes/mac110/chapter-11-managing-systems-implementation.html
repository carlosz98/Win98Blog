Chapter 11: Managing Systems Implementation

Phase 4, Systems Implementation. This phase covers application development, testing, installation and evaluation. Quality assurance runs through all of it, often guided by software engineering and ISO standards (and the CMM / CMMI maturity levels).

Tools by approach: structured development uses DFDs and structure charts; O-O uses UML (use case, class, sequence, state transition); agile uses iterative models and user stories (features plus priority, written by the customer, with test-driven releases after many iterations, as in Extreme Programming (XP)). Generic tools: ERDs, flowcharts, pseudocode, decision tables and trees.

Structure chart symbols: a module (rectangle, a program unit), a data couple (arrow with an empty circle: data passed between modules), a control couple or flag (arrow with a filled circle: a signal or status), a condition (diamond: a module runs only if a condition is true), and a loop (curved arrow: modules repeated).

Creating a structure chart, four steps: review the DFDs and object models; identify modules and their control-subordinate (boss and worker) relationships; add couples, loops and conditions; check it against the documentation.

Cohesion and coupling (know which way is good):

GoalMeaning
CohesionHighEach module does one single task
CouplingLooseModules are independent of each other

Testing, from small to large:

  1. Desk checking: the programmer reads the code for errors.

  2. Code review (structured walk-through): a team reviews the code.

  3. Unit testing: one program or module, alone, with test data. Tested with stubs that stand in for unfinished modules.

  4. Integration (link) testing: programs that work together, tested as a group.

  5. System testing: the whole system with users, including acceptance tests before the users sign off.

Documentation: program, system, operations (for the IT operations group) and user documentation (manuals, help screens, tutorials).

Installation: set up an operational (production) environment with live data, completely separate from the test environment. Every future change is tested in the test environment first. Training should be by role, in groups, using trained people to train others, with interactive, self-paced methods working best. Data conversion should be automated where possible, with strict input controls.

Four changeover methods (very likely on the test):

MethodHow it worksCostRisk
Direct cutoverOld system stops, new one starts the same dayLowestHighest
Parallel operationOld and new run side by side for a timeHighestLowest
Pilot operationOne group or site uses the new system firstMediumMedium
Phased operationOne module at a time across the whole companyMediumMedium

Post-implementation evaluation reviews the system and the team's work. It is best done by people not on the project, soon enough that memories are fresh but after users have had time with the system. The final report to management includes final documentation, planned enhancements and project costs; it closes development and opens the system's operational life.

Likely test points

  • The four changeover methods ranked by cost and risk.

  • The testing levels in order: unit, integration, system (and acceptance).

  • High cohesion and loose coupling are both desirable.

  • Data couple vs. control couple on a structure chart.

  • Test environment vs. operational environment.
