Chapter 9: Data Design

Phase 3, Systems Design. Data design decides how the system stores data. Older file-oriented (file processing) systems keep data in separate files, which causes data redundancy and inconsistent data. A database is linked tables managed by a DBMS.

Why a DBMS is better: scalability, organization-wide access, economy of scale, data sharing, balancing conflicting user needs, enforced standards, controlled redundancy, better security, flexibility, programmer productivity, and data independence (programs do not depend on how data is physically stored).

DBMS components: interfaces for users, the database administrator (DBA) and related systems; a data manipulation language (DML); a schema (the full definition of the database, with subschemas for user views); and the physical data repository. Data warehousing stores data for easy analysis, and data mining finds patterns, including clickstream storage and market basket analysis.

Data vocabulary:

TermMeaning
EntityA person, place, thing or event we store data about
Field (attribute)One characteristic of an entity
Record (tuple)All the fields for one instance of an entity
File / tableA set of records (file in file systems, table in a database)
Primary keyField(s) that uniquely and minimally identify a record
Candidate keyAny field that could be the primary key
Foreign keyField(s) matching the primary key of another table; links the tables
Secondary keyField(s) used to sort or retrieve records (not unique)
Common fieldAn attribute that appears in more than one entity, used to link them

Entity-relationship diagram (ERD): entities as rectangles, relationships as diamonds (or labeled lines). Three relationship types:

  • One-to-one (1:1): one office manager runs one office.

  • One-to-many (1:M): one customer places many orders.

  • Many-to-many (M:N): many students take many courses. It is resolved with an associative entity (ENROLLMENT) that holds both primary keys.

Cardinality describes how many instances of one entity relate to the other. Crow's foot notation shows it: a bar means one, a circle means zero (optional), a crow's foot means many.

Normalization removes problems in table design, step by step:

  1. 1NF: no repeating groups.

  2. 2NF: in 1NF, and every nonkey field depends on the entire primary key (no partial dependency; only an issue with a combination key).

  3. 3NF: in 2NF, and no nonkey field depends on another nonkey field (no transitive dependency).

A memory trick: every nonkey field depends on "the key, the whole key, and nothing but the key."

Codes shorten data entry and storage: sequence, block sequence, classification, alphabetic (category, abbreviation, mnemonic), significant digit, derivation, cipher and action codes.

Storage: logical storage is data as the user sees it; physical storage is binary data on media. Formats include EBCDIC, ASCII, binary and Unicode. Dates can be ISO (YYYY-MM-DD) or absolute (days from a set starting date).

Controls: limit access, encrypt data, back up and recover, keep audit-trail files and internal audit fields.

Likely test points

  • Primary vs. candidate vs. foreign vs. secondary key.

  • Draw an ERD with 1:1, 1:M and M:N; resolve an M:N with an associative entity.

  • Read crow's foot notation.

  • Normalize a table to 3NF and say why each step was needed.

  • DBMS advantages over file processing; data warehouse vs. data mining.
