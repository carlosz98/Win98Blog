Chapter 6: Object Modeling

Phase 2, Systems Analysis. Object modeling describes a system as objects (people, places, events, transactions) that hold both their data and the processes that act on it. Structured analysis keeps data and processes separate; O-O does not. Objects become reusable code modules later.

Three core ideas:

  • Encapsulation: an object is a black box; its data and methods are hidden inside and reached only through messages.

  • Polymorphism: the same message means different things to different objects ("compute pay" for hourly vs. salaried staff).

  • Inheritance: the strongest relationship. A child class gets the attributes and methods of its parent class.

The six UML diagrams in this chapter:

  1. Use case diagram: actors (stick figures) and their use cases (ovals). An include relationship reuses a use case; an extends relationship adds optional steps.

  2. Class diagram: boxes with class name, attributes and methods, joined by lines that show cardinality (one-to-one, one-to-many, many-to-many, such as 1 and 0..*).

  3. Sequence diagram: a dynamic view of one use case over time. Objects sit along the top, with lifelines (dashed lines down), messages (arrows), and focuses (thin bars showing when an object is active).

  4. State transition diagram: how one object moves between states (circles or rounded boxes) because of events (arrows).

  5. Activity diagram: like a horizontal flowchart of actions and events, often with swim lanes.

  6. Object relationship diagram: an overview of the objects and how they interact.

Organizing the model: at the end, use cases are grouped into packages and the class, sequence, state transition and activity diagrams are drawn. CASE tools keep it consistent and support reuse. A business process model (BPM) can also show the people, events and interaction.

Likely test points

  • Define class, instance, attribute, method, message.

  • Explain encapsulation, polymorphism and inheritance with an example.

  • Match each UML diagram to what it shows.

  • Read cardinality notation on a class diagram.

  • Parts of a sequence diagram: lifeline, message, focus.
